01 · 一个连接，两组方向状态

SND.UNA 是最早未确认字节的序号，SND.NXT 是下一个发送序号；RCV.NXT 是下一期待接收序号。每个端点都同时维护发送和接收状态。

02 · 一份报头同时描述两个方向

A→B 报文的 SEQ 标记 A 的数据；ACK 确认 B 的数据；WIN 通告 A 自己还能接收多少 B 的数据。三个字段不能按同一方向解读。

首轮双方同时发送时，A 的 ACK 仍为 5001，B 的 ACK 仍为 1001。各收到对方的 200 B 后，下一轮才分别变为 5201、1201。确认可以捎带在数据中，也可单独发送；纯 ACK 不消耗序号。

本步还受 200 B 和剩余待发数据限制。

真实 TCP 的流控与拥塞控制还共同约束发送。常见近似：max(0, min(rwnd, cwnd) - FlightSize)；另受 MSS、发送缓存、恢复算法、调度与 pacing 等影响。本图假设 cwnd 足够大。

03 · 应用读写与网络收发分开推进

常见内核实现中，应用写入发送缓冲区，TCP 选择可发数据交给 IP；网卡收包后，内核协议栈校验、处理 ACK、更新接收状态，再让应用读取数据。发送队列保留尚未确认的数据以备重传。

应用的 read 和 write、协议栈的输入与输出可交错调度。一个事件循环或多个线程都能使用全双工 socket；TCP 不要求应用创建两个线程。阻塞调用和应用协议仍会影响程序何时读写。

ACK 不代表业务成功。 数据进入接收端 TCP 后，即使应用没有读取，仍然可以被确认。需要业务处理完成的证据时，应由应用协议定义响应。

04 · 为什么零窗口不会封住反向 ACK？

B 的 WIN=0 表示 B 暂无空间容纳 A 的常规新数据。它不要求 B 停止发数据，也不要求 B 停止接收纯 ACK。主图的 B→A 数据可以继续捎带对 A 的确认与 WIN=0。

两条流的状态分别维护，但性能仍可能被共享带宽、CPU、应用读写方式和反向 ACK 可达性耦合。「独立」不意味着永远互不影响。真实 TCP 还会发送零窗口探测，本例省略。

FIN 则用于关闭发送方向：A 发完 FIN 后仍可接收 B 的数据。图中「允许发送新数据」开关只暂停发送调度，不发送 FIN，也不模拟半关闭。

为什么 TCP 可以同时收发？

TCP 的全双工意味着：同一个连接提供 A→B 和 B→A 两条字节流，双方可以在发送本方向数据的同时，接收另一个方向的数据。TCP 没有「轮到谁说话」的协议步骤，也不要求先把一个方向发完，再开启另一个方向。RFC 793 §2.7

1. 一个连接，两套方向状态

连接两端都兼任发送者和接收者。概念上可以画成：

A 的应用 → A 发送缓冲 → A 的发送状态 ──数据──→ B 的接收状态 → B 接收缓冲 → B 的应用
A 的应用 ← A 接收缓冲 ← A 的接收状态 ←──数据── B 的发送状态 ← B 发送缓冲 ← B 的应用

发送状态记录哪些字节已经发出、哪些已被确认、还能发送多少；接收状态记录接下来期待哪个字节，并组织收到的数据。每个方向有自己的字节编号，因此 A 发到第 1201 号、B 发到第 5201 号完全可以同时成立。这些是逻辑状态，不要求实现为两个独立进程或两块固定内存。RFC 9293 §3.3.1

收发缓冲区让应用和网络可以按不同节奏推进：应用把数据交给发送侧，TCP 负责后续传输；数据抵达接收侧后，可以先进入接收缓冲区，等应用读取。Linux 也分别提供发送和接收缓冲区设置；实际缓冲区的内存大小与对外通告的窗口数值不能简单画等号。Linux tcp(7)

2. 同一个报文可以同时「发自己的、确认对方的」

看 A→B 的一个 TCP 报文，三个字段分别回答三个问题：

字段 站在 A 的角度解释 对应的数据方向
SEQ 这段载荷的第一个字节编号是多少？ A→B
ACK 我接下来期待收到 B 的哪个字节？ B→A
WIN 从这个确认位置开始，我允许 B 再发多少字节？ 限制 B→A

这里假定 ACK 标志有效、连接已经建立；窗口缩放等细节暂不展开。ACK=N 累计确认对方在 N 之前的连续字节。A 报文中的 ACK 不是在确认 A 自己发送的数据。 RFC 9293 §3.1

假定握手已完成，A 的下一个数据序号是 1001，B 的是 5001，双方各发送 200 B：

时刻 A→B B→A
双方交叉发出数据 SEQ=1001, LEN=200, ACK=5001 SEQ=5001, LEN=200, ACK=1001
各自收到对方数据后 A 发出 ACK=5201 B 发出 ACK=1201

第一次发包时，双方尚未收到交叉而来的数据，所以 ACK 仍是原来的值。收到后，A 期待 B 的 5201 号字节，B 期待 A 的 1201 号字节。这些数字按字节累加，不是按报文个数累加。

确认可以捎带在下一段反向数据中，也可以用没有应用载荷的纯 ACK 报文发送。不需要等反向业务产生数据，才能确认收到的内容。 RFC 793 §3.9

3. 为什么不必「发一包，等一包」？

滑动窗口允许一个方向存在多个尚未确认的数据段。发送者只要仍有可用额度，就可以继续发送；确认抵达后，额度又向前移动。这使传输能在等待网络往返期间继续推进。RFC 793 §2.6

两个方向各自执行这个过程。A 发数据不需要先取得 B→A 的「使用权」，B 也不需要等 A 暂停。并发能力来自协议允许两条流分别推进，缓冲区和状态管理使这种能力能够落实。

试一下：让 B 停止读取

如果 B 的应用不再读取，已经抵达的 A→B 数据会逐渐占满 B 的接收缓冲区。B 通告的接收窗口可能降为 0，A 因而暂停该方向正常的新数据发送。实际 TCP 仍会进行零窗口探测，避免错过窗口重新打开的通知。RFC 9293 §3.8.6.1

此时 B→A 仍有可能继续传输：B 的发送侧和 A 的接收侧仍可工作，且 A 仍能发回 ACK。B 的 WIN=0 描述的是「B 接收 A 数据的能力」，没有把「B 发送数据的能力」也设为 0。

这不代表两个方向性能完全无关。如果共用链路、CPU 或内存遇到瓶颈，或者确认报文不能及时抵达，另一个方向也可能变慢甚至停滞。应区分「协议上没有要求互相等待」与「运行时没有共享资源」。

4. TCP 的同时，与物理链路的同时

TCP 位于 IP 之上，数据最终由下面的网络逐段承载。TCP 要求的底层服务是数据报传递，并不要求端到端拥有一条专用电路。RFC 793 §1.1、§2.5

由这种分层关系可以推知：即使路径中有一段共享介质需要轮流传输，例如通常共享信道的 Wi-Fi，TCP 的两条字节流仍可在同一时间区间内持续推进。那一段介质上，比特可能是在交替传输。图中的双向箭头表示逻辑数据流，不代表两根专用网线。

同理，TCP 全双工也不要求应用开两个线程。一个线程可以使用非阻塞 I/O，按可读、可写事件分别处理接收和发送。线程的代码可能依次执行，网络传输和内核协议处理仍可以在应用两次调用之间继续进行。Linux socket(7)

后端实现细节：状态变量与可发送额度

每端常用三个序号状态描述进度：SND.UNA 是尚未确认的最早序号，SND.NXT 是下一个要发送的序号，RCV.NXT 是接下来期待收到的序号。发送推进 SND.NXT，有序接收推进 RCV.NXT，确认抵达发送侧后推进 SND.UNA。RFC 9293 §3.8

在忽略恢复过程、序号回绕等细节的简化估算中：

正常新数据可发送额度 ≈ max(0, min(rwnd, cwnd) - flight)

rwnd 是对端通告的接收窗口，保护接收方；cwnd 是发送方维护的拥塞窗口，限制对网络的注入量；flight 是已发出但尚未确认的数据量。还需要有待发送数据，并受分段、发送节奏等实现约束。这是额度估算，不是完整发送算法。RFC 5681 §2、§3.1

应用的一次发送调用成功，也不等于对端已经收到。调用可能只是让内核接受了部分或全部待发送数据；发送缓冲区不足时，阻塞调用可能等待，非阻塞调用可能报告暂不可写。TCP ACK 进一步表示对端 TCP 已确认接收相应字节，仍然不能证明对端业务已经处理、入库或持久化；业务成功需要应用协议自己的响应。Linux send(2)、RFC 9293 §3.10.3

5. 关闭发送方向后，还可以接收

TCP 关闭也能按方向进行：A 发出 FIN 表示「A 没有更多数据要发」，B 仍可继续向 A 发送剩余数据，直到 B 也结束发送。RFC 9293 §3.6

在 Linux 套接字接口中，shutdown(..., SHUT_WR) 关闭发送方向，接收方向仍可使用；它与直接关闭整个套接字有区别。Linux shutdown(2)

这提供了另一个检验问题：A 已经发送 FIN，是否就不能再收到 B 的数据？只要连接的接收方向仍然有效，答案是可以收到。
