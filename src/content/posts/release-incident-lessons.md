> 时间说明：2021 年 5 月 19 日，我遗漏了原定任务，发布延期一天；5 月 20 日 19:00 发布后，没有等待回归或观察日志，问题于 5 月 21 日被发现，我也在当天写下反思。本文结合早期《技术工作的思考》中的接口兼容笔记重新整理；兼容笔记未标注具体日期，课程列表响应示例为后续补充。

那次需求是在申请流程中增加一项必填校验。我忘记了原定任务，临近发版才开始补救，最后只能把发布推迟一天。

开发时，我已经知道另一个业务入口能提供的信息与正常入口不同，却没有继续确认两个入口的实际调用情况，也没有把需要关注的差异告诉测试。我按自己的理解完成修改，验证了正常流程，就提测了。

5 月 20 日 19:00 发完版，我没有等待回归结果，也没有查看线上日志，便离开了。直到次日，同事发现了问题。

## 一、清单里要有任务，也要有验证和跟进

当时我记住的是「增加一项校验」，没有把这项工作的依赖、提测时间和发版后跟进一起安排好。遗漏之后，提测和发布安排都需要重新确认。

现在接到一个需求，我会先记下要交付什么、涉及哪些入口、还需要谁提供信息，以及什么时候提测和发布。发布后由谁检查结果，也放在同一条任务里。每天检查一次，比等到临近发版再回忆可靠得多。

计划变化时，要通知受影响的人，并确认他们收到了。当时虽然发布已经推迟，仍有相关人员不知道这个变化。延期会影响测试和后续安排，需要明确同步，不能只在自己与某一个人的对话里结束。

开发中发现的疑问也应该尽早说出来。另一个入口是否能提供新校验需要的信息、产品是否要求所有入口都受同一项约束，都可以在提测前确认。自己没想清楚时直接作决定，会把未经确认的假设带进实现。

## 二、验证影响时，要把旧入口和旧客户端算进去

这次修改里，我没有充分验证两个入口的调用情况。检查影响面时，可以拿各入口的实际请求来确认：哪些字段一直存在，哪些允许缺失，新增条件是否会拒绝原本可以完成的操作。

接口兼容也有同样的问题。服务端可以统一部署，用户却不会同时更新 App。修改请求参数、响应结构或业务条件时，新服务仍要支持约定范围内的旧客户端。

用一个课程列表接口说明。下面的响应是为解释兼容性构造的示例，与当年的事故无关。假设旧客户端从响应根部读取 `items`，用 `count` 计算分页：

```json
{
  "items": [{ "id": 1, "title": "示例课程" }],
  "count": 1
}
```

如果为了统一格式，把列表放进 `data`，并将总数字段改为 `total`：

```json
{
  "data": {
    "items": [{ "id": 1, "title": "示例课程" }],
    "total": 1
  }
}
```

新版客户端按新结构读取，仍然能展示课程，旧客户端读取的位置却已经失效。它可能显示空列表，也可能在解析时报错。服务端即使返回 HTTP 200，也无法据此判断旧版页面是否正常。

如果需求只是增加「是否还有下一页」，可以保留原有字段，在旧结构上补充：

```json
{
  "items": [{ "id": 1, "title": "示例课程" }],
  "count": 1,
  "has_more": false
}
```

这要求旧客户端能够忽略新增字段，且 `items`、`count` 的类型和含义保持原样。严格检查字段的客户端仍需要验证，不能仅凭「只加没删」判断兼容。如果必须采用新的结构，可以提供新接口，并按约定在过渡期维护旧接口。

验证时，用旧客户端的请求调用新服务，检查字段位置、类型、空列表格式和分页含义，再用仍受支持的旧版本或相应客户端测试确认解析和展示。对于后来新增或改为必填的参数，也要验证旧请求是否仍按约定处理。

这些约定可以保存成自动化测试。提测时则要写清新增了什么、哪些旧行为要保留、需要回归哪些入口，让测试人员有明确的检查范围。

### AI 可以帮忙检查，预期仍要有依据

现在用 AI 辅助开发，我会让它先列出相关调用关系、受影响入口和测试用例，再核对源码与实际请求。遇到没有依据的新字段、方法或调用关系，就先确认，不直接进入实现。

如果 AI 根据同一个错误假设生成实现和测试，两者可能一起通过，却都偏离需求。旧请求、旧版本的行为和根据业务规则独立确定的预期，都可以用来检查生成结果。测试通过之外，还要能解释这些预期从哪里来。

## 三、发版后，观察这次修改影响的行为

那次发布，我没有等待回归结果，也没有查看线上日志。测试环境无法覆盖线上所有客户端版本、历史数据和入口组合，发布后仍需要继续验证。

观察项应在发版前确定。对一个涉及校验或响应结构的接口变更，我会关注以下信息：

| 要确认的事情 | 可以检查的信息 |
| --- | --- |
| 原有请求是否仍能完成 | 相关接口的错误日志、错误码、失败数量和失败比例 |
| 不同入口和旧客户端是否正常 | 按入口、客户端版本区分的结果，以及旧版页面的实际操作 |
| 业务结果是否符合预期 | 关键操作的完成情况、返回内容，以及必要的数据抽样 |

日志按相关接口和错误类型筛选；能够取得入口或客户端版本时，再分别看，避免少量旧版本的异常被总体请求量掩盖。比较发布前后的比例变化，也要结合请求量和调用情况判断。

低频入口尚未被调用，就还没有它运行正常的证据，可以安排一次受控验证。观察多久，要看实际调用频率和日志、指标的更新周期。结束观察时，记下已经验证的入口、版本和结果。

出现异常后的处理方式也要提前考虑。恢复原有响应结构，还是回退这次版本，由谁处理、需要同步谁，都应当清楚。如果变更还写入了数据，回退代码未必能撤销数据变化，需要另外检查。

这些内容可以直接附在任务里：兼容验证做了什么，发布后看哪些结果，谁继续跟进，异常时如何恢复。确认相关入口和客户端的表现符合预期后，再结束这次交付。
