> 时间说明：2020 年 5 月 14 日的笔记已写下「功能与测试并行」；2020 年 6 月 13 日进一步记下「一个方法对应一个 ut」，强调减少反复调试长流程的时间。

刚开始写后端业务时，我在笔记里写过：「一个方法对应一个 ut」。反复跑长流程 Debug 很耗时，单独测一个方法，定位问题方便得多。

一个方法的逻辑可能只执行几毫秒，但为了验证它，往往要登录、准备数据、提交表单，再等待后续处理。改一行代码，就把这些步骤重新做一遍，时间很容易花在重复准备和等待上。

AI 写测试的速度常常超出我的预期。把业务规则说清楚，它就能很快生成一份包含初始化数据、测试结构和断言的可运行草稿。原来得手工写的重复代码少了，补一个小测试也就没那么费事了。

## 一、每次修改之后，要等多久才能知道对错

假设一个课程预约功能出了问题：用户明明符合取消条件，页面却提示不能取消。

沿着完整流程排查，需要确认页面提交了什么、接口读到了什么、业务方法判断了什么，最后才能知道错误在哪里。找到可疑方法之后，如果仍然每改一次都重新操作页面，就又要准备一遍数据、重复一遍操作。

也可以在定位到业务判断后，把当时的付款状态和剩余时间固定下来，直接调用这个方法。修改后运行测试，马上知道同一个输入是否得到了预期结果。

假设验证完整流程需要 2 分钟，整理用例、让 AI 生成并审阅局部测试需要 2 分钟，局部测试每轮反馈需要 1 秒，同一问题需要修改 3 轮。共同的定位和代码修改时间不计入两边。

| 工作 | 每轮都跑完整流程 | 先补局部测试 |
| --- | --- | --- |
| 准备局部测试 | 0 | 2 分钟 |
| 三轮修改后的验证 | 6 分钟 | 3 秒 |
| 修复后验证完整流程 | 已包含在最后一轮 | 2 分钟 |
| 合计 | 6 分钟 | 4 分 3 秒 |

这些数字都是假设值，实际耗时还取决于环境、数据准备、编译速度，以及测试需要多少审阅和维护。

小测试准备好后，就可以在后续修改中重复使用。AI 缩短了准备时间，局部运行又减少了每轮验证的等待。

## 二、表驱动测试本身就能表达业务场景

继续用取消预约的例子。先假设产品已经确认了规则：只有已支付的预约可以申请取消，而且距离开始时间至少还有 24 小时。「恰好 24 小时」也符合条件。

先把这句话拆成一张场景表：

| 场景 | 已支付 | 距离开始时间 | 是否符合取消条件 |
| --- | --- | --- | --- |
| 正常申请 | 是 | 25 小时 | 是 |
| 恰好达到时限 | 是 | 24 小时 | 是 |
| 差一分钟达到时限 | 是 | 23 小时 59 分钟 | 否 |
| 未支付 | 否 | 25 小时 | 否 |
| 已经开始 | 是 | 0 | 否 |

读这张表就能讨论业务。「至少」是否包含等于，未支付时如何处理，都已经有了明确答案。表驱动测试把这些行保存到代码里，每行包含一个场景、输入和预期结果，再用同一段测试逻辑逐行验证。

下面是对应的 Go 测试，依赖标准库 `testing` 和 `time`：

```go
func TestCanCancel(t *testing.T) {
	cases := []struct {
		name      string
		paid      bool
		remaining time.Duration
		want      bool
	}{
		{"已支付，提前25小时", true, 25 * time.Hour, true},
		{"已支付，恰好提前24小时", true, 24 * time.Hour, true},
		{"已支付，只提前23小时59分钟", true, 24*time.Hour - time.Minute, false},
		{"未支付，提前25小时", false, 25 * time.Hour, false},
		{"已支付，已经开始", true, 0, false},
	}
	for _, tc := range cases {
		t.Run(tc.name, func(t *testing.T) {
			if got := CanCancel(tc.paid, tc.remaining); got != tc.want {
				t.Fatalf("got %v, want %v", got, tc.want)
			}
		})
	}
}
```

这个小例子只验证取消资格。时间差由调用方传入，测试不用等待真实时间流逝，也不需要启动页面或连接数据库。

对应的业务判断很短：

```go
func CanCancel(paid bool, remaining time.Duration) bool {
	return paid && remaining >= 24*time.Hour
}
```

整理本文时，我用这组用例做了验证：先故意把实现中的 `>=` 写成 `>`，测试准确报出「已支付，恰好提前 24 小时」这一项失败；恢复为 `>=` 后，五个场景全部通过。

预期结果来自已经确认的业务规则。即使实现把「至少」理解错了，测试仍然会保留那个明确的 `true`，把差异暴露出来。

这样的测试表就是一份可执行的业务场景说明。以后需求改变，修改场景和预期，再调整实现，可以直接看出哪些行为发生了变化。

## 三、AI 让「顺手补个测试」变得容易

以前写单测，麻烦常常在准备工作上。要构造输入，给外部依赖安排返回值，写重复的断言，再把正常情况、边界情况和失败情况分别补齐。知道应该写，也容易拖到主流程完成以后。

现在把方法签名、相关类型、业务规则和现有测试风格交给 AI，这些重复工作可以很快完成。对于上面的例子，只要先确认那张表，AI 就能把场景转成测试数据，补上执行和断言。

也可以让 AI 检查场景表：是否漏掉了临界值，某个条件不满足时应该拒绝还是返回其他结果，哪些输入应该产生同样的行为。AI 能很快列出这些问题，业务上的答案仍然需要根据需求确认。

可以这样描述任务：

```text
根据下面已经确认的业务规则，先列出场景、输入和预期结果。
标出规则里没有说明、需要确认的情况。
按确认后的场景表，沿用项目风格生成表驱动测试。
预期结果按业务规则填写，不从当前实现反推。
运行测试，报告失败的场景及实际结果，保留断言供修复后验证。
```

如果只让 AI「给这个方法补测试」，它可能根据当前分支生成用例，把实现里的误解一起写进预期。上面的 `>` 就可能被当成既定行为，恰好 24 小时的结果也被写成 `false`。测试全部通过，业务错误却还在。

审阅时先看场景名和 `want`：每一行预期是否符合需求，失败时是否能暴露对应的问题。

## 四、让小测试持续提供可信的反馈

「一个方法配一个小测试」可以从一个有业务意义的判断开始。它可以包含多行场景，不必机械地给每个简单转发方法都增加测试。

如果为了测一个条件，必须准备数据库、消息队列和完整登录状态，可以检查这个业务判断能否单独接收明确的输入。外部数据如何读取和写入，仍需要相应的集成测试验证；局部测试负责让规则本身容易重复检查。

测试里的等待也要尽量可控。读《Concurrency in Go》时整理的心跳笔记，就讨论过等待工作开始信号的做法。并发测试可以等待明确的就绪或结果事件，同时保留启动和完成的时间上限。随意加一段 `sleep`，容易把反馈重新变成等待和猜测。

局部测试通过后，再验证受影响的接口和完整流程，确认输入确实传对了，保存和后续处理也符合预期。
