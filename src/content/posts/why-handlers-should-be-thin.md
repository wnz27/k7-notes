翻看刚参加工作时的笔记，我发现自己给 Handler 留了一句很用力的提醒：「薄薄薄」。

当时我已经知道要分 Model、Service、Handler，但落实到一个具体需求，仍然需要判断每段代码该放在哪里。一个接口既要解析参数，又要查询数据、判断业务条件、保存结果，直接写在 Handler 里最顺手。多建一个 Service，似乎只增加了一次调用。

笔记里还有一条更具体的约定：Handler 只调用 Service，由 Service 组合 Model 的方法。即使有些请求可以直接调用 Model，也先经过 Service。

现在回看，这条约定有助于建立边界，但还需要解释清楚：哪些事情应该留在 Handler，哪些事情移走以后才更容易修改和测试，以及简单功能是否值得付出分层成本。

## 一、先明确三个名字各自负责什么

本文沿用早期笔记里的叫法，讨论一个普通后端应用中的职责划分。

| 层次 | 主要职责 | 以发布文章为例 |
| --- | --- | --- |
| Model | 表达业务实体的属性，以及实体自身的规则 | 文章有哪些状态，草稿能否转为已发布 |
| Service | 组织一次业务操作，协调所需的实体与数据访问 | 读取文章和作者，检查发布资格，完成发布并保存 |
| Handler | 接收请求，把输入交给业务操作，再转换返回结果 | 解析文章 ID、取得操作者身份、调用发布方法、生成响应 |

Model 在不同项目里可能指数据库表结构，也可能包含业务方法。这里强调的是实体及其自身规则。数据库读写可以由模型承担，也可以单独放到数据访问代码中，具体取决于项目已有的组织方式。

同样，Service 在这里指应用内组织业务操作的代码，并不要求部署成一个独立服务。这几个名字只是约定，判断职责时还要看方法实际做了什么。

## 二、跨实体的业务流程，由 Service 组织

用一个简化的文章发布需求来推演。假设发布前需要满足三个条件：文章处于草稿状态，作者拥有发布资格，当前操作者有权管理这篇文章。这个例子用于说明分工，不对应一次真实的线上改造。

「文章能否从草稿变成已发布」围绕文章自身展开，适合放在 Article 的业务方法里。这样，其他入口修改文章状态时，也能使用同一条规则。

「作者是否拥有发布资格」可以由 Author 表达。但完整的发布操作需要同时知道文章、作者和操作者的信息，还要安排检查与保存的顺序。把整个流程塞进 Article，就会让文章对象承担查作者、识别操作者等额外职责；放进 Author，也会遇到类似问题。

Service 可以接收文章 ID 和操作者 ID，读取所需数据，检查权限与发布资格，再调用文章自己的发布方法并保存结果。Article 保留状态变化的规则，Service 负责组织这次操作。

这里的「上移」描述的是业务流程的归属。判断时要看规则由谁负责、依赖哪些信息。跨表查询仍可以留在数据访问代码中；只涉及一个实体的复杂规则，也可以继续留在实体内部。实体之间存在关联本身很正常，需要避免的是让某个实体负责整个应用流程。

原笔记里「需要其他 Model 时就上升一层」的说法，适合作为初步判断。继续追问一次，通常更容易划清边界：这段代码是在描述一个实体的行为，还是在组织几个对象共同完成一件事？

## 三、把业务规则从请求入口中分出来

发布文章的 Handler 仍然有自己的工作。它需要解析请求，检查文章 ID 的格式，从可信的认证结果中取得操作者身份，然后调用 Service。业务完成后，它还要把结果或错误转换成约定的响应。

这些工作可能需要不少代码，因此「薄」不能简单按行数判断。检查 JSON 能否解析、ID 是否为有效整数，属于请求处理；判断文章是否允许发布、操作者是否有发布权限，属于业务规则，应该在业务层保证。

如果把发布资格和状态判断都写在 HTTP Handler 里，将来增加一个命令行入口或后台任务时，就要复制这些判断，或者让新入口依赖 HTTP 请求对象。规则变化后，也容易只修改其中一个入口。

把完整操作放在 Service 后，不同入口可以调用同一个发布方法。HTTP Handler 负责 HTTP，后台任务负责读取任务参数，各自处理输入与返回方式，发布条件由同一处保证。

测试也更容易安排。检查「作者没有发布资格时拒绝发布」，可以直接测试业务方法；检查「非法 ID 返回参数错误」，再测试 Handler。业务规则的验证不必每次都从完整的 HTTP 请求开始。

## 四、从一个真实片段看职责，别只看目录名

我的 Coding-Daily 仓库里有一个 serverdemo 练习项目。它的 `biz`、`service`、`data` 三份 README 都只有标题，不过源码里可以看到调用关系。

下面节选自 `internal/service/greeter.go` 的 `SayHello` 方法：

```go
g, err := s.uc.CreateGreeter(ctx, &biz.Greeter{Hello: in.Name})
if err != nil {
	return nil, err
}
```

这里把请求中的 `Name` 转为业务对象，交给 `CreateGreeter`，并处理返回错误。方法后面还有读取环境变量、组装响应的代码。

继续看 `internal/biz/greeter.go`，业务方法如下：

```go
func (uc *GreeterUsecase) CreateGreeter(ctx context.Context, g *Greeter) (*Greeter, error) {
	uc.log.WithContext(ctx).Infof("CreateGreeter: %v", g.Hello)
	return uc.repo.Save(ctx, g)
}
```

在这份代码里，`service` 目录承担了本文所说的 Handler 职责，`GreeterUsecase` 对应组织业务操作的 Service，`Greeter` 是模型，`data` 提供数据访问实现。目录名相同，职责未必相同，读代码时要沿着调用关系确认。

这个示例也有明确的局限：`CreateGreeter` 只记录日志并调用 `Save`，而 `data` 中的 `Save` 直接返回传入对象，没有实际写入数据库。它能展示结构，无法证明复杂业务已经得到合理拆分。

这个示例也适合用来讨论：简单操作是否需要中间层？

## 五、简单 CRUD 可以按实际成本决定

如果一个小工具只是按 ID 查询一条记录，所有 Service 都只把参数原样传给下一层，那么增加这些方法的直接收益确实有限。可以先用简单结构完成需求，等出现共享规则、多个入口或跨实体操作时，再提取明确的业务方法。

已经采用统一分层的团队，也可以保留很薄的 Service。统一调用方式能减少协作中的选择成本，并为后续规则留下位置。代价是文件和调用层次增加，阅读简单功能时要多跳转几次。

原笔记要求即使只是转发调用，也要封装一层 Service，在当时有助于养成习惯。现在再用这条约定，我会结合项目规模、团队约定和真实需求判断，不要求每张表都机械地配上一套 Service，也不会提前建设一组没有实际用途的基类。

即使保留 Service，也要继续检查其中的职责。把 Handler 里的全部代码搬进一个几百行的方法，只改变了位置。实体自己的规则仍应留给实体，数据库读写细节也应放在适合维护的位置。

## 六、从一个现有接口开始调整

想检查一个 Handler 是否承担过多职责，可以先给其中的代码标出三类工作：请求与响应转换、业务条件与执行顺序、数据读取与保存。

然后找出一段完整的业务操作，给它一个能表达目的的方法名，比如 `PublishArticle`。让它接收业务需要的参数，逐步移走对 HTTP 请求和响应对象的依赖。需要跨实体协调的步骤放进 Service，实体自身的判断保留在实体中。

调整后，用业务条件检查结果：同样的数据从另一个入口进入，发布规则是否仍然成立；只改变响应格式时，是否可以只改 Handler。再用相应的业务测试和接口测试确认原有行为。

再读那句「薄薄薄」，我会把它当作一条检查提醒：Handler 里是否留着一段业务判断，让其他入口也需要重新实现一遍。
